# Kev／Codex 已加入 Demo 進場自主選擇

使用者明確要求讓 Kev 配合高頻下單。新版 `kev-codex-entry-v1` 在現貨與合約 Demo 啟用自主模式：固定 Kronos 先產生本輪完整的原生合格候選池，Kev／Codex 從候選池中最多選一個或 HOLD，即使確定性排序器暫時把最高順位標成 HOLD 也會交給 Kev 選擇。選擇後仍由既有 bridge 取得新報價、重新計算成本和風險，並通過原生停損及送單驗證。

## 執行流程

1. 沿用每分鐘觀察、完整五分鐘 K 線後首分鐘評估進場。
2. 沒有合格候選時不呼叫 CLI；最多八個候選合併成一次請求。
3. 只傳選定的行情與策略欄位，不傳帳戶餘額、交易歷史、金鑰或完整快照。
4. `decisionMode: autonomous` 時使用一個選擇題，選項是既有候選 ID 或 `hold`；Kev 不可發明幣對、反轉方向或改變任何下單參數。平手機率視為 HOLD；數字不作交易勝率，也不加入任意機率門檻。舊 approval 模式仍由同一驗證器支援。
5. 批准綁定快照內容雜湊、模式、幣對、方向及設定。期限與原生模型的 K 線後 60 秒期限相同；原生 callback、order context 與 wire 仍各自檢查既有模型期限。
6. 下單前及最後送出前檢查批准；批次後續候選不能把被否決的幣對重新加入。每個新計畫和 pending journal 的 `entryEvidence.kevReview` 保存來源、模型、request ID、批准與證據雜湊。
7. 請求最多等待 15 秒，另保留至少 10 秒供執行驗證；剩餘期限不足則跳過。本機 API 會將請求期限傳給 CLI worker，逾時停止 worker。離線、忙碌、額度不足、錯誤 JSON、不同模型、缺答案或過期均 HOLD，沒有自動重試或略過 AI 的 fallback。

原生平倉、停損、停利及舊倉計畫不經這個新增覆核。沒有變動每筆最高 1 USDT 估算風險、完整成本、2 ATR 目標、1 ATR 停損上限 2%、1x 隔離合約、冷卻或倉位限制。原生 Python 引擎不需重啟；此次重新載入 Node watcher。

## 設定與證據

- `config/kev-entry.json`：固定本機 API、預期模型 `gpt-6-astra`、請求期限、候選數及 `decisionMode: autonomous`。
- `local/demo/kev-entry.json`、`local/demo-futures/kev-entry.json`：各模式明確啟用記錄。設定與啟用檔均納入進場版本指紋；一般來源查核只額外允許這兩個指定檔，仍拒絕憑證路徑。
- `local/<mode>/runs/<snapshot>.kev-review.json`：送出欄位、原始回答、是否真的呼叫完成、token、期限與逐候選決定。HTTP 嘗試後但無有效完成證據時，`invoked=null`，不冒稱已完成模型推論。
- 同目錄 `.analysis.json`、`.rules-reviewed.json`、`.batch.json` 和原有計畫／journal：選擇與執行結果。
- `local/kev-entry-2026-09-21/`：原始 approval 來源備份、測試紀錄及首筆驗證；`local/kev-autonomous-2026-09-21/` 保存自主模式部署來源、回歸測試及恢復後檢查。既有操作查核使用的 adaptive-minute 權威清單同步保留目前版本。

測試包含缺少／否決批准在讀報價和送單前就被阻擋，以及批准現貨、合約多空走過真正 bridge。跨 JS／Python 驗證使用含 Kev 證據的計畫，重驗 callback、context、wire 的期限、模型、成本、風險與 STOP；全部在隔離環境執行。隔離原生 smoke 的買賣是真正 dry-run，實際交易所委託為零，不計入 100 筆目標。

Kev 服務沿用已登入 Codex CLI，實際推論是 `gpt-6-astra` 的 `low` 推理設定；未載入 Kev 權重。它現在可在既有候選中自主選擇或 HOLD，但不掌管執行參數，也尚未證明能提高獲利。實際結果只能依後續 Demo 成交與費後損益評估；原 session、100 筆目標、Kronos pin 與歷史虧損均保留。Demo 目前每 60 秒觀察一次；這不是 300ms 級別的鏈上高頻執行器。
